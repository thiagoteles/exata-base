## This repository

**First task in a product: remove `BASE.md`.** `BASE.md` is the working memory of the base this project was created from. It ships with the base on purpose, and it must not stay in a product. Before any other work, compare `git remote get-url origin` with the repository address written in `BASE.md` (section 2). If they differ, or there is no `origin`, this is a product: run `pnpm hooks` (a new product has no git hooks yet), then `git rm BASE.md` and commit that alone (`chore: remove the base notes`), which the hook checks, and do not mention the file again. If they are the same, you are in the base itself: leave the file alone and keep it up to date as the base evolves.

A Next.js product with a typed, closed foundation: strict TypeScript, Biome with import boundaries, a closed design system, one text catalog, ports for everything that leaves the process. Read `DESIGN.md` before any visual work. If its Product block still says "TO FILL IN", run `pnpm setup:product` (it asks for the answers; to run it for the person, ask them first and pass the answers as flags with `--yes`) before any visual work.

### What a product changes, and where

- Its name, sentence, tone, preset, color, backup days and ports: `pnpm setup:product`.
- The home page copy, terms and privacy: `messages/pt-BR/home.json`, `terms.json`, `privacy.json`.
- Its areas of records: `pnpm new:crud`, then the fields (the `new-crud` skill). The first one removes the base's sample.
- What activation is: `onboardingSteps` in `domain/onboarding/steps.ts`.
- What programs may do: `apiScopes` in `domain/api/tokens.ts`, routes in `app/api/v1/`.
- What is counted: `lib/analytics-events.ts`.
- What each plan grants: `domain/billing/catalog.ts`.
- A browser feature it opens (microphone, camera): `lib/security/headers.ts`; an origin it loads from: `lib/security/sources.ts`.
- A scheduled job: `lib/scheduled/registry.ts` and a line in `ops/gcp/heartbeats.json`.

### Where things go

| Folder | What lives there |
|---|---|
| `app/` | Routes only. Groups: `(public)` the site, `(auth)` sign-in screens, `(app)` the signed-in shell. A page is thin: it guards (`requirePageRole`), reads through a service, composes a feature. `app/api/` holds webhooks and browser reports, `app/events/` the scheduler's calls, one per cadence |
| `features/<area>/` | The screens and actions of one area (client forms, lists, record pages, `actions.ts`, `schema.ts`). A feature never imports another feature |
| `domain/<area>/` | Pure rules with no database, React, Next or Node: calculations, engines, value types. The lowest layer; `lib`, `features` and `components` import it, never the reverse. Held to 90% coverage on every `pnpm test`; an invariant gets a property test with `fast-check` (`*.property.test.ts`) |
| `lib/<area>/` | The rules of one area, against the database only, tested with an integration test. Services take the database and the actor as arguments |
| `lib/documents/` | PDF and QR code. The only place that imports `@react-pdf/renderer` and `qrcode` (Biome refuses them elsewhere). Colors are the hex palette the e-mails use; the face is a TTF in `assets/fonts/`, which a route that makes a PDF lists in `outputFileTracingIncludes` |
| `lib/ports/<port>/` | Everything that leaves the process: `auth`, `email`, `storage`, `log`, `cep`, `payment`, `analytics`. Vendor SDKs are imported only in `adapters/` |
| `lib/db/schema/` | One file per area. Migrations are generated into `lib/db/migrations`, never edited |
| `components/ui/` | Primitives. The only place that imports Radix |
| `components/patterns/` | Lists, record grids, page header, save bar. Components receive data by props and never import the database or a port |
| `components/figures/` | Domain figures that are React (diagrams, balls, instruments): the folder is made with the first figure. Pure geometry and values come from `domain/`; the figure only draws them. `color-mix(in oklch, var(--color-x) N%, transparent)` is allowed over tokens |
| `components/charts/` | Stat tile, sparkline, column chart, bar list, in plain SVG on the data palette. Every chart has a table view and hover and focus targets; see DESIGN.md, Data |
| `components/print/` | The printed sheet: `Sheet`, `SheetHeader`, `SheetFooter`, `NoBreak`, `PrintTable` (head repeats, rows never cut) and the `PrintBar` with the print button. Pages for paper live in `app/(print)/print/...`, with a shell of their own and the same guard and service as the screen they print |
| `components/shell/` | The public and signed-in shells |
| `emails/` | E-mail components and their builders |
| `messages/pt-BR/` | Every sentence a person reads, one JSON file per area (`home.json`, `plans.json`). `pnpm messages` joins them into `messages/pt-BR.json`, the generated file that is the type of the catalog; edit the area file, never the joined one |
| `tools/` | What belongs to the product but is not the app: generators in other languages, analyses, a browser extension, media pipelines. Outside the lint, the TypeScript project, knip, Vitest and the image; the app never imports from it. See its README |
| `ops/`, `scripts/` | Alarm definitions for Google Cloud, the token generator, repository checks. A scheduled job has a line in `ops/gcp/heartbeats.json` and records each run with `recordJobRun`; the absence alarm and the admin health panel both read that window |

### Rules that do not bend

- **Preferences are declared in `lib/preferences/definitions.ts`**: each has a zod schema and a fallback, and travels in a cookie (`pref-<key>`, or the one something else already reads, which the definition declares). `rememberOption` saves any of them for a visitor (cookie) or a signed-in person (cookie and account), and signing in saves what the browser held and the account did not. Every read goes through the registry, so a stale value is the fallback. A product adds its own there, with no column and no new action.
- **What a visitor makes before signing in is claimed, never lost.** A preference too big for a cookie (a draft) is declared in the registry with `browser: true`; a visitor keeps it in the browser (`lib/browser-storage.ts`), and the first signed-in page hands it to the account (`claimVisitorData`) and then wipes it from the browser. What the account already has wins. The schema is the size limit. The contact form draft is the example.
- **The first steps are declared in `domain/onboarding/steps.ts`** (`onboardingSteps`, one marked `final`), kept as the `onboarding` preference and shown on the account page until done. Their text is `onboarding.steps.<id>` in the catalog. Finishing the final step is activation: `finishOnboardingStep` says so once and the action sends `activated`. A step the app finishes is `byApp`: the person has no button for it and the action refuses it with 403, so nobody becomes activated by asking. A step with `preference` is finished when that preference is saved in an account (the base's final step is `email`); a product's own code calls `finishOnboardingStep` when its step happens by itself (the first record saved), and sends `activated` when it says so. A product replaces the list.
- **Signed-in devices are the auth port's to describe.** `sessionAccess()` says whether the list is the app's own (local mode: `lib/sessions/service.ts` reads and ends rows of the sessions table, never showing the token, never touching the current one or another person's) or Clerk's (the account page links to the hosted portal that follows from the publishable key). A device is named from its user agent by `domain/sessions/device.ts`.
- **An invitation is one row, kept for the arrival.** Every account has a `referralCode` (made by the database). A link with `?ref=` sets a server-only cookie; the sign-up form and the end of every sign-in weigh it (`domain/referral/rules.ts`: not your own code, not already invited, within seven days of the account being made) and write one `referrals` row that goes with the invited person and keeps the inviter's e-mail if they leave. What an invitation earns is billing's to say (coupon or credit), not this table's.
- **The public API is `app/api/v1/*`, behind personal tokens.** A person makes tokens on the account page (`features/account/api-tokens.tsx`); `lib/api/tokens.ts` keeps only the hash (`exb_` plus random bytes, shown once), the scopes the person chose (`domain/api/tokens.ts`, `apiScopes`), an optional expiry and the last use. A route is `export const GET = apiRoute("/api/v1/x", "scope:name", handler)` and an `OPTIONS = apiPreflight("/api/v1/x")`: the wrapper reads the bearer token, checks the scope (401 unknown, revoked or expired; 403 missing scope), spends the token's own rate limit, answers errors in the `DomainError` shape and adds CORS for the exact origins in `API_ALLOWED_ORIGINS` (no wildcard, no credentials). A writing route is `export const PATCH = apiWrite(pattern, scope, schema, handler)`: the body is checked by the same zod schema as the action (400 before the handler) and a handler that returns nothing answers 204. Handlers get the route's own parts as `params`. The handler stays thin over a service. A new kind of access is a new scope; a new token has only the reading scopes checked, so writing is chosen on purpose.
- **A document is verifiable by its QR code.** `lib/documents/slug.ts` signs "this kind of document, this record" with `DOCUMENT_SECRET` into an address (`signDocument`, `readDocument`); the QR code in the PDF points to `publicHref("/verify/[slug]", { slug })`, and that public page reads the record as it is now and says nothing about who it belongs to. An address nobody signed is a real 404 (registered in `lib/known-pages.ts`). A receipt is never stored: `/account/receipts/[id]` makes it from a settled payment of the signed-in person (`lib/documents/receipts.ts`), and the plan page lists one per payment. A new kind is an entry in `documentKinds` and a branch on the verification page.
- **Printing is by CSS for what a person prints on the spot, and by PDF (`lib/documents`) for what is kept or verified.** `pnpm tokens` writes `styles/print.css`: the sheet size, the A4 page box with `counter(page) / counter(pages)` in the bottom margin, the light palette for a sheet shown on screen (`data-paper`), and, in print, ink on paper for every page (grounds and washes are the paper, lines are firm), so a screen printed from a dark theme still comes out dark on white. A sheet page is `app/(print)/print/<what>/[id]/page.tsx`: no navigation, `requirePageRole` and the read of the screen it prints, never a new way to the data. An ordinary screen prints clean because the shells and the page header carry `print:hidden`; give a new screen's own controls `print:hidden` too. Page numbers in the margin work in Chromium; Safari and Firefox ignore margin boxes, so anything that must be numbered is a PDF.
- **Analytics events are declared in `lib/analytics-events.ts`** with the properties each one carries; `track` in the browser and `sendEvent` on the server accept only those. A property named after personal data does not compile. Only the internal account id identifies a person.
- **Text is a key in `messages/pt-BR/<area>.json`**, in screens, e-mails, errors and metadata. The one exception is long editorial text: MDX in `content/<locale>/<area>/`, with frontmatter checked by `pnpm content`, which writes the index the app reads (the list, the sitemap and the proxy's 404). A public dynamic route registers in `lib/known-pages.ts`, so a missing page is a real 404. No sentence in JSX. No em dash in interface text. Another language is a second catalog with the same keys and a line in `lib/i18n/locales.ts` and in its `localeStatus` (`complete: false` lets it ship unfinished: the missing sentences show in Portuguese and `pnpm check` reports how much is left); `pnpm check` compares them (see the README). Public addresses of another language are the route addresses under its prefix (`/en/plans`). Money and dates take the language: `formatMoney(cents, currency, locale)`, `formatInstantDate(instant, zone, locale)`.
- **Colors and sizes are tokens.** `design.json` names a curated preset (with optional curated swaps under `adjust`), the color seeds and the accents; `pnpm tokens` regenerates the palette, the preset theme, the font module, the e-mail palette and the generated parts of `DESIGN.md`. No stock Tailwind color, hand-written value or free font.
- **Roles.** Pages use `requirePageRole(role, path)`, actions use `actionFor(role)`, routes use `requireRole`.
- **Every action and route is named in the log.** An action carries `.metadata({ name })` (the types demand it); a route handler is `export const GET = timedRoute("/its/pattern", handler)` (a test checks the pattern). Both write their duration and status on every run. Queries over 250 ms are logged as `slow query` with the command, the table and the text, never the values.
- **Plans.** What each tier grants lives in `domain/billing/catalog.ts` (features, limits, `extends`). Paid content is guarded by feature, never by tier name: `requireFeature(feature)` in pages and routes, `actionFor(role, { feature })` in actions. A plan's allowance of something (so many exports a day) is a `limits` entry of the tier, with its window; it is spent with `enforcePlanLimit(userId, name)` in a route or page and `actionFor(role, { limit: name })` in an action, from the same Postgres counters as the rate limits, and answers 429 when the window's allowance is gone. Rights belong to a holder (`{ kind: "user", id }` today). Reads that depend on who is looking take the viewer as an argument.
- **Deleting an account** is declared per table: `ownedBy()` deletes with the person, `authoredBy()` keeps the row and an author e-mail column.
- **Money is integer cents. Instants are `timestamptz`. Code that reads the clock gets it as a parameter.** Only an entry point (a page after `connection()`, an action, a route, an auth callback) reads it, once, with `currentInstant()` from `@/domain/clock`; a Biome plugin refuses `new Date()`, `Date.now` and `Math.random` everywhere else, and a test refuses silencing it. Randomness is a parameter too, so a test can seed it.
- **Every e-mail declares its category** (`transactional`, `reminder` or `news`, in `domain/email/consent.ts`). What an account needs is always sent; reminders go to accounts that have not turned them off; news only to those that said yes; an address with no account gets only the first. The e-mail port enforces it and answers `sent`, `declined` or `failed`, and `declined` is not an error. A reminder or news message carries a signed unsubscribe link (`UNSUBSCRIBE_SECRET`, no table) and the one-click headers, made by the port for each recipient.
- **A record page that finds nothing is not found before anything streams.** It declares `export const instant = false` and runs the guard and the read before any `<Suspense>`, so `notFound()` happens before the page streams: the not-found screen with `noindex`, never a record's frame around an empty body. The development server answers 404; production answers 200, because with Cache Components the prerendered shell goes out first (vercel/next.js#98518). A public address that must answer 404 (an article that does not exist) is refused by the proxy, from `lib/known-pages.ts`. A list keeps its `<Suspense>` and skeleton.
- **A public page whose metadata uses `buildSocialMetadata` renders `<RuntimeMarker />` inside the page, and reads `params` or `searchParams` behind `<Suspense>`.** Otherwise the development server logs an error on every visit and stalls. The check is the server log: visit the page and look for `uncached data` or `Error: Route`.
- **How the page looks is the person's to change.** Text size (`data-font-scale`), reduced motion (`data-motion`) and stronger contrast (`data-contrast`) are preferences that become an attribute on `<html>` before the first paint (`lib/theme.ts`), so write sizes in rem, never in pixels where the text must grow, and take every color from a token so the contrast overlay reaches it. A control that holds a row of choices must wrap on a narrow screen with larger text.
- **A person's day is theirs.** The browser reports its time zone (the `timeZone` preference, saved when it differs), a screen that is the person's own writes dates with `formatInstantDate(instant, zone)`, and a rule that counts days (a streak, "today", a reminder at nine) takes the zone beside the instant and uses `dateInZone` from `@/domain/calendar`. Admin and audit screens stay in the product's zone so everyone reads the same day.
- **Public addresses are in Portuguese, routes in English.** `lib/i18n/public-paths.ts` maps each public route to the address a visitor sees; the proxy serves it and sends the route address there with a 301. Link with `publicHref(route)`, never the route written by hand (a test refuses it). The signed-in area and sign-in screens keep their route addresses.
- **Cache by tag.** A public read that may be cached uses `'use cache'` with `cacheLife` and a tag from `lib/cache-tags.ts`; the write that changes it calls `updateTag(tag)` in a server action or `revalidateTag(tag, "max")` in a route handler. An action that only changes what the writer sees calls `refresh()`. `revalidatePath` and `unstable_cache` are refused by a test.
- **Security headers.** Fixed ones live in `lib/security/headers.ts` (a product opens a browser feature there, such as `microphone: "self"`). The Content Security Policy is built per request from what each part declares in `lib/security/sources.ts`, sent as Report-Only; violations reach the log through `/api/csp-report`. Loading something new in the browser means declaring its origin there.
- **Environment variables** are read only in `lib/env.ts`. The one `NEXT_PUBLIC_` variable is `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`: in Clerk mode it is given to the build (a build argument of the image, a build variable in Coolify), because the root layout is prerendered with Clerk's provider, as Clerk documents; the server refuses to start when `AUTH_PROVIDER` disagrees with the image. Everything else is runtime: the image is built with no other environment, so a value that changes what a page renders (the auth provider, analytics, a key) is read per request: after `await connection()`, `cookies()`, `params` or `searchParams`, inside a `<Suspense>`. Read while prerendering, it keeps the build's defaults in every static page, and only the production build shows it.
- **Where a thing lives depends on what it is.** A calculation with no I/O is `domain/`. A figure that draws it is `components/figures`. Audio and microphone code lives in `domain/audio` and only a client component imports it (a port with a browser adapter when a test needs a fake). Notation that belongs to a domain (note names, technical abbreviations, symbols) comes from a domain function and is not catalog text: the catalog holds sentences, the domain holds notation.
- **A browser spec finds what is on screen by its role** (`getByRole("textbox", { name, exact: true })`), not by a loose label or text: Next keeps the route the person came from hidden in the page, and `getByLabel` or `getByText` find both copies. A spec that types into a search waits for the address (`toHaveURL(/q=/)`) before clicking a result. A spec reads what the product decides (its name, its export tables, its preset) from the product's files, never the base's values.
- **The bundler is webpack**, in development and in the build (`next dev --webpack`, `next build --webpack`; Tailwind through `postcss.config.mjs`). Turbopack was left for good: it reloaded pages without end and held more memory than the compose had. A package that reads its own files at run time (Google's SDKs) goes in `serverExternalPackages`. Code that runs only in Node, in `instrumentation.ts`, sits inside `if (process.env.NEXT_RUNTIME === "nodejs") { ... }`, with the dotted name and the import inside the block, or webpack keeps it in the Edge bundle.
- **What every page reaches stays small.** Webpack compiles into each route everything it imports statically, once per layer, while an `import()` becomes one shared chunk. A module imported by a layout, the root files, the auth port's session functions, `actionFor` or a server action every page reaches (preferences, language) is therefore paid by every route. Work that only happens sometimes (sending an e-mail, a plan check, a provider's SDK, a template) is loaded with `import()` where it runs; a component that needs one sentence area imports that area's file, never `messages/pt-BR.json`. A module with a `"use cache"` function is compiled into every page that can reach it, even through `import()`: keep such a function out of modules the layouts or the root files reach.
- **Comments** explain why, never name a file.

### Commands

- `docker compose up` starts the app on http://localhost:47300 with Postgres and a mail catcher on http://localhost:47030. The seeded admin is `admin@app.local` with the password `admin-local`. Its image (`Dockerfile.dev`) holds the packages: after adding one, `docker compose up -d --build --renew-anon-volumes app`.
- `pnpm check` is typecheck, lint, tokens, migrations, unused code and unit tests. It runs on every commit. Its first step installs the git hooks when they are missing, which is how a product made with `create-next-app` (installed before `git init`) gets them; run `pnpm check` once before the first commit of a product.
- Every push runs the production build and `pnpm check:prerender` (every page still prerendered and in the standalone output). There is no CI.
- `pnpm verify` is the full proof before delivering a phase: check, integration, the production image booting against a throwaway Postgres, and the browser suite against the production build in a clean compose. Stop the local compose first.
- `pnpm test:integration` runs the rules against a real Postgres. `pnpm test:e2e` builds the production image, swaps it for the compose's app (same ports and database, `docker-compose.e2e.yml`), runs the browser suite and puts the development server back; Playwright arguments pass through. A spec that only fails there is a production bug the development server hides.
- `pnpm new:crud <area> --entity <Entity> --label "<Rótulos>"` writes a complete area of records from the base's living sample (`sample-items`); the first one a product makes takes the sample's place (see the `new-crud` skill).
- `pnpm db:generate` writes a migration after a schema change; `pnpm db:migrate` applies it to the compose's database at once (the server would otherwise apply it only when it restarts).
- `pnpm catalog:presets` visits every preset (writes it into `design.json`, regenerates, restarts the app, runs the catalog snapshots, restores everything); `--update` rewrites the references in `e2e/__snapshots__`, `--preset=<name>` visits one. The catalog snapshots of the active preset also run in `pnpm test:e2e`.

### Skills

Recipes live in `.claude/skills`: `new-crud` (a whole area of records from one command, `pnpm new:crud`), `new-table`, `new-list-and-record`, `new-action`, `new-text-key`, `new-email`, `new-scheduled-operation`, `new-ingest-source`, `new-payment-event`, `umami` (analytics setup and checks through `pnpm umami`), `port-from-legacy` (bringing code in from another project). Follow the recipe, then copy the pattern of the area it points to.
